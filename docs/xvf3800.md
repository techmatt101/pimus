# ReSpeaker XVF3800

The default microphone array, and the one on every amp today, is a Seeed
ReSpeaker XVF3800 USB 4-Mic Array (the other choice, selected per unit with
`respeaker_board`, is the [ReSpeaker Lite](respeaker-lite.md)). It is
an XMOS VocalFusion XVF3800 voice processor (an xcore.ai chip running XMOS's
`sw_xvf3800` firmware in its USB-accessory build) with four PDM microphones, a
12-LED ring, and a speaker jack, on one USB device with ids `2886:001a`. This
page is what an engineer or an agent needs to know about it before touching the
voice path: what the chip does, what the Pi sees over USB, which module owns
each part, and how to test and tune it. The XMOS documentation it distils is
linked at the end; read that for anything this page does not cover.

Seeed's firmware is XMOS's with the LED ring added and different power-on
defaults. The XMOS documentation describes v3.2.1 of the stock firmware; the
Seeed units here report `2.0.10`. The pipeline and the control commands match,
the defaults do not always, so read a value back before assuming it.

## What the chip does

The XVF3800 is not a microphone. It runs a complete far-field voice pipeline on
the array and hands the Pi the result:

1. **Microphone inputs** — four PDM microphones, converted to PCM and processed
   at 16 kHz throughout (the USB interface runs at 48 kHz and is resampled at
   the edge).
2. **Acoustic echo canceller (AEC)** — an adaptive filter per microphone that
   subtracts the far-end signal, which is whatever the room's speaker is
   playing. It needs that signal as a reference; without one it cancels
   nothing. It converges at start-up on the first far-end audio it hears and
   re-converges when the acoustic path changes.
3. **Beamformer** — three beams: one free-running beam that scans the room for
   new talkers, two focused beams that track individual talkers. An auto-select
   stage picks the best beam as the output. Each beam has an azimuth
   (direction of arrival) and a speech energy the host can read back.
4. **Post processor** — dereverberation, stationary and non-stationary noise
   suppression, an equaliser, automatic gain control, and a limiter. This is
   the *Conference* (communications) output: tuned for a person to listen to.
5. **ASR output** — a second tap taken after the beamformer and *before* the
   post processor, with a fixed gain instead of AGC. Wake-word and
   speech-recognition engines do worse on non-linear processing, so this is
   what the assistant is given.

Key figures from the datasheet, for anyone reasoning about timing:

| Parameter | Value |
| --- | --- |
| Internal processing rate | 16 kHz |
| AEC tail length | 192 ms |
| AEC reference channels | 1 (mono) |
| Reference delay the AEC can absorb | 0 to 500 ms |
| Input delay, microphone to output | at least 58 ms |
| Beamformer update time | 16 ms |
| Operating distance | 0.3 m to 5 m |
| Noise suppression | up to 25 dB |

## What the Pi sees over USB

One UAC2 audio device in adaptive mode at 48 kHz, plus a vendor control
interface on endpoint 0 and a DFU interface.

**Capture is two DSP outputs, not a stereo pair.** The XVF3800's output mux
puts one signal on each channel:

| Channel | Seeed default | What it is |
| --- | --- | --- |
| 0 (left) | Conference | Auto-selected beam through the full post processor. Voiced for people. |
| 1 (right) | ASR | Auto-selected beam straight from the beamformer, fixed gain, no noise suppression. Thin and pumpy to a human ear; what the wake word wants. |

Recording the device as mono downmixes the two, which is why the audio manager
lifts exactly channel 1 into its own mono source and the voice assistant is
told to capture one channel. In stock XMOS firmware the ASR output is off and
the right channel is silence; Seeed's build ships it on. The mux is
reconfigurable at run time (`AUDIO_MGR_OP_L`, `AUDIO_MGR_OP_R`), so if a unit's
recordings ever sound wrong on both ears, read those back.

**Playback is the AEC reference.** The device's stereo playback endpoint feeds
the echo canceller; only the left channel is used and the right is ignored. The
speaker jack plays that same reference, which is why headphones plugged into
the ReSpeaker carry the music and follow the volume dial: the jack exists to
let you hear what the DSP is being told the room hears. Nothing is normally
connected to it. The datasheet is explicit that the reference must match what
the room hears, so the reference path is held at unity gain end to end.

**Control** is USB vendor requests: `bmRequestType` `0x40` to write and `0xC0`
to read, `wValue` 0, `wIndex` the resource id, `bRequest` the command id with
bit 7 set for a read. A read answers with a status byte ahead of the payload;
anything but 0 means the servicer has not produced this command's answer yet
and the bytes behind it belong to the previous command. The servicer advances
every few milliseconds, so reads are paced and retried rather than hammered.

## Which module owns what

| Device feature | Owner | Setting |
| --- | --- | --- |
| ASR capture channel published as the mono default source | `apps/audio-manager/src/audio_manager/xvf3800/microphone.py` | `smartamp_voice_capture_channel` (default 1) |
| Voice assistant capture | `smartamp-voice-assistant.service.j2` hardcodes `--audio-input-channels 1` | never raise this; a second channel is forwarded to Home Assistant as a far-end reference |
| AEC far-end reference loopback (HiFiBerry monitor into the XVF3800 playback sink, pinned at 100%) | `apps/audio-manager/src/audio_manager/xvf3800/aec.py` | `smartamp_aec_reference_enabled`, `smartamp_aec_reference_match`, `smartamp_loopback_latency_ms` |
| Capture card profile after a USB power cycle | `microphone.py` `activate_capture_card` | — |
| LED ring frames (vendor commands, resource 20) | `apps/controller/src/voice/xvf3800-device.mts` | `respeaker_led_enabled`, `respeaker_led_brightness` |
| Which face each voice state shows | `apps/controller/src/voice/led-states.mts`, faces in `voice/leds/` | compiled in, not inventory |
| Reading speech energy and direction of arrival for the listening ripples | `xvf3800-device.mts` reads `AEC_SPENERGY_VALUES` (resource 33, command 80) and `AUDIO_MGR_SELECTED_AZIMUTHS` (resource 35, command 11); `voice/mic-sensor.mts` levels them | — |
| `xvf_host` command-line tool on the Pi | `ansible/roles/smartamp/tasks/voice.yml`, pinned by commit and checksum in `vars/main.yml` | `make update-versions` |
| Health checks | `smartamp-doctor` looks for `2886:001a` on the bus and `aec_reference.available` in the status file | — |

The LED commands (resource 20: effect, brightness, speed, colour, DoA colour,
ring colour) are Seeed's addition and are not in the XMOS command appendix.
The controller records the whole set but asks the firmware only for the `Ring`
effect, streaming one colour per LED itself, and `Off`. The firmware's own
breath, rainbow, solid, and direction-of-arrival effects are deliberately
unused: they cannot follow live audio, and they would be a second way of
saying what the ring looks like.

Two facts about the mounting are compiled into `mic-sensor.mts`: the DSP
counts azimuth from the USB socket, which sits half a turn round the ring
from LED 0, and speech energy has no documented scale (it moves with gain and
distance), so the sensor levels it against a decaying running peak rather than
a fixed number.

## The reference path and its timing

The AEC models the echo as *the reference, delayed and filtered by the room*.
The routing policy and the acoustic validation are separate:

1. **Level.** The reference sink and the bridge stream into it are pinned at
   100% and unmuted while active. This makes host-side attenuation predictable;
   DSP gain, headroom and external gain compensation still need measurement.
2. **Presence.** The reference is the HiFiBerry output monitor, so it carries
   music, the assistant's own voice, aux and USB. However, the DSP uses only
   the left reference channel; stereo coverage remains unverified. It is
   torn down with the other idle bridges after `smartamp_idle_teardown_seconds`
   of silence, because with nothing playing there is no echo to subtract, and
   rebuilt within a second of the next stream.
3. **Timing.** The reference crosses a PipeWire loopback
   (`smartamp_loopback_latency_ms`, 20 ms) and USB before the DSP sees it, while
   the sound reaches the microphones through the air almost at once. The AEC
   needs a causal reference: it must arrive before the echo. A long echo-filter
   tail does not imply tolerance of a late reference. `AUDIO_MGR_SYS_DELAY`
   uses 16 kHz samples: positive values delay the reference, negative values
   delay the microphones. Measure both DSP taps together before changing it.

See the [XMOS tuning guide](https://www.xmos.com/documentation/XM-014888-PC/html/modules/fwk_xvf/doc/user_guide/04_tuning_the_application.html)
and the [validation checklist](audio-reliability-actions.md#aec-and-microphone-validation).

## Checking the AEC

Use controlled broadband noise for convergence/timing measurements, then music
and speech for real-use cancellation tests. `AEC_AECCONVERGED` stays set after
an earlier convergence; it cannot certify the current route or acoustic path.
Record its value as supporting evidence, not a pass/fail verdict:

```sh
sudo xvf_host AEC_AECCONVERGED
```

Never send full-scale, unbounded `/dev/urandom` to the default output. Prepare
a short, attenuated stimulus and explicitly select a verified playback bus;
the [action checklist](audio-reliability-actions.md) defines the measurement order.

To hear what the assistant hears, record both capture channels together and
listen with headphones: left ear Conference, right ear ASR. Judge room and
placement from the left, judge what the wake word has to work with from the
right.

```sh
ssh office-amp.local "sudo -u smartamp XDG_RUNTIME_DIR=/run/user/\$(id -u smartamp) \
  timeout 15 parecord --device=\$(pactl list sources short | awk '/XVF3800/ && !/monitor/ {print \$2; exit}') \
  --channels=2 --file-format=wav /tmp/mic.wav"
```

The status file at `/run/user/*/smartamp-audio-status.json` reports endpoint
presence as `aec_reference.endpoints_available` and a configured active stream
as `aec_reference.available`. These are routing checks, not signal measurements.

### Measurement traps

Each of these produced a wrong conclusion once. Do not repeat them.

- **PipeWire-side lag is not DSP-side lag.** Cross-correlating the HiFiBerry
  monitor against the XVF3800's USB capture includes about 130 ms of capture
  latency that varies per `parecord` run and that the DSP never sees. A
  loopback latency "aligned" from that made the true reference acausal and
  measurably hurt cancellation.
- **Music makes correlation lags wander.** What looked like clock drift was
  the correlator following the music's self-similarity. White noise gives a
  stable lag, drifting about 2 ms over 12 s, which is ordinary clock ppm the
  AEC tracks without help.
- **`xvf_host --get-aec-filter` is not an impulse response.** It dumps
  frequency-domain filter blocks (12 × 256 floats per microphone). Peak
  positions in it mean nothing without XMOS's analysis script.
- **Level comparisons across `SHF_BYPASS` or AGC states are confounded** by
  the pipeline gains between them (the beamformer adds about 6 dB, then AGC,
  on top of `AUDIO_MGR_MIC_GAIN` and `AUDIO_MGR_REF_GAIN`). Use the
  matched processing states and controlled stimuli when comparing residuals.
- **The controller shares the device.** Its reads and writes are serialised
  against each other inside one process, but `xvf_host` is another process,
  so a read from either can occasionally answer with the other's payload.
  Repeat an implausible reading; stop `smartamp-controller` for a careful
  measurement session.

## Tuning with `xvf_host`

Provisioning installs Seeed's prebuilt `xvf_host` under
`/opt/smartamp/xvf3800-host-control` and links it onto the `PATH`. It speaks
the same vendor-control protocol as the controller. Every value it writes is
volatile: a power cycle, `REBOOT`, or a `USB_BIT_DEPTH` write restores the
firmware defaults. Volatile changes can still be loud or break capture; record
the baseline and change one parameter at a time. **Never run
`save_configuration`** to persist a change: on this firmware it can stop the
device enumerating over USB outside safe mode
([Seeed issue #8](https://github.com/respeaker/reSpeaker_XVF3800_USB_4MIC_ARRAY/issues/8)).
A setting that proves out belongs in the repository, applied at start-up, not
in the device's flash.

```sh
sudo xvf_host VERSION                 # 2 0 10 on the Seeed firmware; proves the control path
sudo xvf_host --list-commands         # every command with its type and range
sudo xvf_host --dump-params           # every current value
sudo xvf_host AUDIO_MGR_SYS_DELAY     # read
```

The commands this project has needed, with the XMOS-documented defaults and
what the Seeed units were observed to hold:

| Command | Access | What it is | XMOS default | Seen on Seeed 2.0.10 |
| --- | --- | --- | --- | --- |
| `VERSION` | read | Firmware version, three bytes | `3 2 1` | `2 0 10` |
| `AEC_AECCONVERGED` | read | 1 once the echo filters have converged | 0 | 1 within 3 s on noise |
| `AEC_AECPATHCHANGE` | read | 1 while the AEC is re-converging after the acoustic path changed | — | — |
| `AUDIO_MGR_SYS_DELAY` | read/write | Reference-versus-microphone delay in 16 kHz samples, −64 to 256 | −32 | stock |
| `AUDIO_MGR_REF_GAIN` | read/write | Gain on the reference before the AEC | 1.5 | 8 |
| `AUDIO_MGR_MIC_GAIN` | read/write | Gain on all four microphones before the AEC | 10 | 90 |
| `AEC_FAR_EXTGAIN` | read/write | External attenuation of the reference, in dB, for the DSP to allow for | 0 | −20 at host volume 0 dB |
| `AEC_ASROUTONOFF` | read/write | 1 puts the ASR output on the mux's category 7; 0 leaves AEC residuals there | 0 | not read back; channel 1 carries ASR |
| `AEC_ASROUTGAIN` | read/write | Fixed linear gain on the ASR output, 0 to 1000 | 1.0 | — |
| `AUDIO_MGR_OP_L` / `AUDIO_MGR_OP_R` | read/write | Output mux for each USB capture channel as `(category, source)`; see the user guide's Output Selection table | `(8,0)` / `(0,0)` | not read back; XMOS's ASR recipe is `AUDIO_MGR_OP_R 7 3` |
| `AEC_AZIMUTH_VALUES` | read | Azimuth in radians of focused beam 1, focused beam 2, the free-running beam, and the auto-selected beam | — | — |
| `AEC_SPENERGY_VALUES` | read | Speech energy per beam in the same order; above 0 means speech | — | read by the controller |
| `AUDIO_MGR_SELECTED_AZIMUTHS` | read | Processed direction of the current talker (NaN with none) and the auto-select beam's azimuth | — | read by the controller |
| `AEC_RT60` | read | The room's reverberation time estimate in seconds; negative while invalid | — | — |
| `PP_AGCONOFF`, `PP_AGCGAIN`, `PP_AGCMAXGAIN`, `PP_AGCDESIREDLEVEL` | read/write | The Conference output's automatic gain control; `PP_AGCGAIN` is always applied and `PP_AGCONOFF` only decides whether it adapts | on, 32, 125, 0.0045 | — |
| `SHF_BYPASS` | read/write | Bypasses the AEC and beamformer entirely | 0 | — |
| `REBOOT` | write | Reboots the chip and resets every parameter | — | — |

The ASR output is still on channel 1 after the power cycles that reset every
value written by hand, so Seeed's defaults are baked into its build rather than
saved to flash. Nobody has yet read the mux back on a unit; doing so is the
first step if the two capture channels ever sound alike.

## Wake word over music

Measured on office-amp with music at normal volume and speech from the usual
spot, polling the ducking state as the wake detector:

| Speech-band peak at the ASR output | Above the music residual (−41 dBFS) | Woke? |
| --- | --- | --- |
| −35 dBFS | +6 dB | no |
| −27 dBFS | +14 dB | no |
| −25 dBFS | +16 dB | yes |
| −19 dBFS | +22 dB | yes |
| −17 dBFS (a shout) | +24 dB | yes |

These are historical observations from one placement and configuration, not
proof that AEC works for every source, channel or level. They suggest testing
speech level after reference coverage and cancellation have been measured;
they do not establish a universal threshold for `okay_nabu`.

After that baseline, the available levers are Linux Voice Assistant preferences, live on
the satellite device in Home Assistant (Settings → Devices & services →
ESPHome → the amp; some sit under configuration or diagnostic) and stored in
`/var/lib/smartamp/lva/configuration/preferences.json`:

1. **Mic auto gain** (`mic_auto_gain`, 0–31 dBFS, off by default). WebRTC AGC
   inside the assistant lifts weak speech toward a target before the wake
   model hears it. Compare it with the unchanged baseline; do not prescribe a
   target before checking clipping, residual music and false wakes.
2. **Wake word sensitivity** (`wake_word_1_sensitivity`, unset means the
   model's default of about 0.7). Widens the net at the cost of occasional
   false wakes.
3. **Noise suppression** (`mic_noise_suppression`, 0–4). Leave at 0. It is
   single-channel WebRTC suppression of *steady* noise with no reference
   input, so it barely touches music and smears speech. The XVF3800's AEC is
   the only stage that uses the music as a reference.

A preference value that proves out should be baked into the repository as an
inventory default passed through `smartamp-voice-assistant.service.j2`, so a
re-provision or a wiped preferences file cannot silently lose it. If wake over
music is still weak, investigate the remaining path/timing and model failures
before considering a second software canceller. Cascading echo processing is
not an established fix and would need a separate measured comparison.
